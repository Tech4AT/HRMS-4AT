# Development

## Layout

```text
4AT-HRMS/
├── docs/       — this documentation
├── frontend/   — Next.js app (unchanged from the original HRMS-Frontend repo)
└── backend/    — Django + DRF backend (implemented on the RBAC branch,
                see docs/IMPLEMENTATION-STATUS.md)
```

## Frontend

```bash
cd frontend
npm install
cp .env.example .env.local   # set BACKEND_API_URL
npm run dev                  # runs on http://localhost:3001
```

- Dev/start scripts pin the port to **3001** (`next dev -p 3001` / `next start -p
  3001`).
- `frontend/src/app/api/*` are Next.js route handlers that proxy to the Django backend
  at the URL in `BACKEND_API_URL` (server-side only, not exposed to the browser). The
  default in `.env.example` is `http://localhost:3000/api/v1` — i.e. it expects the
  backend on port **3000**, mounted at `/api/v1/`.
- The frontend was moved from its own repository into `frontend/` with no code
  changes — it has no hardcoded absolute paths and no repo-location dependencies
  (confirmed: `tsconfig.json` paths, `next.config.ts`, and `.env.example` are all
  relative/config-driven). `AGENTS.md`/`CLAUDE.md` at the frontend root are
  regenerated by `next dev` itself and are safe to leave as-is.
- `npm run lint` runs `next lint`. There's no test suite configured yet in this app.
- **No backend yet?** Set `MOCK_AUTH=true` in `.env.local` (see `.env.example`) to sign
  in with any email/password — the four `app/api/auth/*` and `app/api/users/me` route
  handlers short-circuit to a fake org-scoped admin user instead of calling
  `BACKEND_API_URL`. Login screen, `AuthProvider`, and the cookie session flow are
  otherwise unmodified. Every other proxied endpoint (`/api/employees`, `/api/leave`,
  etc.) still requires the real backend. Remove `MOCK_AUTH` from `.env.local` (or set it
  to anything other than `true`) once Phase 1's real auth endpoints are live — see
  `src/lib/api/mock-auth.ts`.

## Backend (implemented — see IMPLEMENTATION-STATUS.md)

Built on the RBAC branch. The local workflow (per
[IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md)):

```bash
cd backend
docker compose up -d          # Postgres
cp env.example .env
python manage.py migrate
python manage.py createinitialadmin
python manage.py runserver 0.0.0.0:3000   # matches the frontend's BACKEND_API_URL
```

- Settings are split into `base.py` / `dev.py` / `test.py` / `prod.py`, selected via
  `DJANGO_SETTINGS_MODULE`.
- Tests run with `pytest-django` against a real Postgres instance (no sqlite) — use
  `--reuse-db` for fast iteration, `--create-db` after a migration change.
- DRF responses are camelCase (via `djangorestframework-camel-case`) to match the
  frontend's contract; write Django code in normal `snake_case`.

## Running both together

1. Start Postgres + backend on **:3000** (mounted at `/api/v1/`).
2. Start the frontend on **:3001** with `BACKEND_API_URL=http://localhost:3000/api/v1`.
3. Log in through the frontend at `http://localhost:3001` — it proxies through its own
   `api/*` route handlers to the backend; there is no direct browser → Django call.

See [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md) for the exact request/response
contract (`/auth/login`, `/users/me`, cookie attributes, error shape, pagination
shape) the backend has to match for the frontend to work unmodified.

## Environment variables

Never commit real secrets. Each app keeps its own `.env.example` with placeholder
values:

- `frontend/.env.example` — `BACKEND_API_URL`, and a temporary `MOCK_AUTH` flag
  (see below) for working on the frontend before the backend exists.
- `backend/env.example` (Phase 0 task `P0-E4-02`) — DB credentials, JWT signing
  secret, S3 keys, SMTP settings, once the backend is scaffolded.
